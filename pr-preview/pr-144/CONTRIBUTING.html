Contributing ​

Coach Poulpy is built mostly by talking to Claude, using Matt Pocock's engineering skills. This page says which skill to reach for, in what order, and what each one leaves behind in the repo or on GitHub.

Everything below works the same in a Claude Code terminal (type /triage, /to-spec...) and in a Claude project thread (write "triage #12" or "run to-spec on this"). Skills marked auto are picked up by Claude without being named.

The flow ​

Rounded boxes are where work starts; each step leaves something behind, listed in the table below.

Which skill when ​

You haveUseIt leaves behind
A loose idea/grill-with-docsSharper terms in CONTEXT.md, an ADR when a hard-to-reverse choice is made
An idea you can only judge by trying it/prototypeThrowaway code, never merged
A grilled idea worth more than one session/to-spec, then /to-ticketsA spec issue, then ready-for-agent sub-issues with blocked-by links
A small, grilled change/implementA branch with tests, reviewed by /code-review
Issues you didn't write (bugs, requests)/triageLabels, triage notes or an agent brief on the issue
A bug that resists a first look/diagnosing-bugsA fix with a regression test
A huge effort with no clear path/wayfinderA wayfinder:map issue whose tickets are decisions, handed to /to-spec when clear
A module that feels wrong/codebase-design autoA smaller interface at a cleaner seam
A question to research/research autoA cited Markdown note in the repo

/tdd, /grilling, /domain-modeling, /code-review and /writing-for-agents are auto: the skills above call them, and Claude reaches for them when a task fits.

Habits that keep it working ​

  • One goal per thread or session. Grill, spec and tickets in one unbroken conversation; then each ticket starts fresh, because the ticket carries everything it needs.
  • Don't triage what /to-tickets made. Those issues are born ready-for-agent.
  • Read the area's rules. docs/agents/areas.md has what the Architect, Designer, Poulpy and Translator used to carry in their heads, per area. A spec or ticket reads the sections it touches; one review per PR covers the rest.
  • Words come from CONTEXT.md. If an issue or a test needs a word the glossary lacks, add it there first.
  • A decision that would surprise the next reader gets an ADR in docs/adr/, in the same PR that makes it.
  • Every PR says Closes #n, so merging closes the issue.
  • Branch names say what the work is: <type>/<issue-number>-<short-description>, in English, like feat/21-training-plans or fix/34-rest-timer-sound. Leave out the number when there is no issue (docs/brand-decisions). Types are feat, fix, docs, chore and design. No random suffixes, session ids or tool prefixes such as claude/.
  • The docs site is the source of truth, so a PR is reviewed there. On every PR, the Docs site workflow publishes a preview and posts a "Review in the docs" comment, both without an agent. It links each spec, mockup, decision or guideline the PR adds or changes, down to the sections and glossary entries it touches, and the agreed mockups drawn for the issue the PR closes. Agents don't write a review comment of their own; anything the reviewer must know, such as a known difference from a mockup, goes in the PR description.
  • Every guideline is on the docs site. A new rule, glossary or ADR is published in the same PR that adds it: add its file to site/published.mjs and a sidebar entry in site/.vitepress/config.mts. CI fails on a Markdown file the site doesn't publish or a page no link reaches.
  • CI is not a phone. Anything about Bluetooth, sound, haptics, background running or installs carries the device-test label and is checked on a real phone before merge.

Labels ​

Every issue has one type, one state and at least one area, and sits in its phase's milestone. The labels are defined in .github/labels.yml and synced to GitHub when that file changes on main.

GroupLabels
Typebug, enhancement, documentation
Stateneeds-triage → needs-info, ready-for-agent, ready-for-human or wontfix
Areaarea:shared, area:android, area:ios, area:devices, area:catalog, area:server, area:web, area:design
Checkdevice-test
Wayfinderwayfinder:map, wayfinder:research, wayfinder:prototype, wayfinder:grilling, wayfinder:task

How agents read the tracker and the domain docs is in docs/agents/.

Running and checking the code ​

See the README for building each app. Before opening a PR, at least run:

sh
./gradlew jvmTest jsTest :server:test :tools:i18n:test
node design/build-tokens.mjs --check
node design/build-poulpy.mjs --check

When a change touches Markdown, CI also lints it, checks its links and checks the site publishes it. To run the same checks first (lychee is a separate install, see its README):

sh
npx markdownlint-cli2
lychee --config lychee.toml './**/*.md'
(cd site && npm ci && npm run build && node check-published.mjs)
