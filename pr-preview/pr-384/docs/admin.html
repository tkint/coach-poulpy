The admin area ​

The admin area is where the maintainer looks after the catalog, the accounts and the server's settings. It is a section of the website under /admin, backed by routes under /api/v1/admin/. The work is tracked in #26.

Who can open it ​

  • Admin is a role on the account (member or admin), not a scope anyone can ask for (ADR 0020).
  • Only the website's sign-in reaches it. An admin route answers 401 to an anonymous caller and 403 to anyone who is not an admin signed in through the website: a member, an admin on the phone app, a personal access token or a third-party app.
  • The website signs in with cookies (POST /api/v1/web/session, see the API). The server reads the access cookie only for the website client, and a write whose Origin is not the website's gets 403, which is the CSRF defence of ADR 0020. The API answers the website's origin with Access-Control-Allow-Credentials, so the page calls it with credentials: 'include'.
  • One admin for now. There are no finer rights.

The screens ​

The admin lives at /admin on the website (mockups). With no admin session it shows the sign-in; the page asks GET /api/v1/me, and a member who signs in is signed out again at once with the same "wrong email or password" message, so the screen never says who is an admin. Once signed in it shows the CpDrawer shell, with the audit log, the accounts, the settings and the status. The sidebar lists only the screens that exist; each admin feature adds its own entry. A Coach Poulpy app link at the bottom of the sidebar goes back to the web app.

Accounts ​

The Accounts screen is a paged table of every account (mockups, details, filtered, no match, delete). Each row shows the email, role, whether the email is confirmed, whether sign-in is blocked and the creation date. Every column sorts (a click flips the direction); the email filter matches part of the address and the role, email status and sign-in filters narrow the list. Eight accounts show per page, with CpPagination and the count below. Picking a row opens its details in the CpSidePanel, floating over the page from the right with a dim backdrop (the table never moves; a click outside or Escape closes it). The state is in the address (/admin/accounts?q=…&role=…&sort=…&order=…&page=…&account=<id>), so a view can be bookmarked and the back button steps through it (Navigation lives in the URL); the audit log is /admin. Nothing here shows a workout or health data. The panel holds three actions, each written to the audit log with the account's id as the target (never its address):

  • Disable blocks sign-in and signs every device of the account out, access and refresh tokens included. It is reversible: Enable lets the account sign in again. A disabled account is refused at sign-in with the same "wrong email or password" answer as any other refusal.
  • Delete removes the account and every row of it through the same code as the user's own deletion, once the admin has typed the account's email again.
  • An admin can't disable or delete their own account (409 own-account).

Filtering, sorting and paging happen on the server (AdminAccounts.list, which reads every account row and cuts the page in memory, enough for a back office; move it into SQL if accounts reach the hundreds of thousands). The routes are GET /api/v1/admin/accounts/{id} for one account (a link opens an account that isn't on the page), GET /api/v1/admin/accounts with q, role, confirmed (yes/no), signIn (active/disabled), sort (email, role, confirmed, signIn, created), order, page and size, answering {accounts, total} (a word that isn't allowed is a 400 bad-query), POST /api/v1/admin/accounts/{id}/disable, POST /api/v1/admin/accounts/{id}/enable and DELETE /api/v1/admin/accounts/{id} with {"confirmEmail": …}, all described in the OpenAPI document and all for an admin signed in through the website.

Settings ​

The Settings screen at /admin/settings changes the server without a deploy (mockups, invalid address, test sent, test failed). Its one setting so far is the from-address of the emails.

  • Only non-secret settings live in the database, one row per setting in the settings table (ServerSettings). The SMTP host, port, user and password stay in the environment (Deploying the server) and are not shown or editable here.
  • MAIL_FROM is the default until a from-address is saved. A saved one applies to the next email, with no restart: every email goes through SettingsMailer, which reads the setting when it sends. An address alone (hello@example.com) or with a name (Coach Poulpy <hello@example.com>) is accepted; anything else is refused (400 invalid-address) and nothing is saved.
  • Saving writes admin.settings.mail-from to the audit log, with the masked address (h***@example.com) as the target.
  • Send test email sends a message to the signed-in admin's own address with the saved settings and shows whether the mail server took it or, in crimson with an icon, what it answered (535 Authentication failed).
  • The last send is remembered. SettingsMailer.last keeps when the last email (a test or any other) went, which kind it was, to whom (masked) and the mail server's error if any, for the Status screen. It lives in memory, so a restart forgets it.

The routes are GET /api/v1/admin/settings ({mailFrom, mailFromSaved}), POST /api/v1/admin/settings/mail-from with {"mailFrom": …} and POST /api/v1/admin/settings/test-email ({sent, error}), for an admin signed in through the website. The screen keeps no state of its own beyond its path.

Status ​

The Status screen at /admin/status says what the server can do right now (mockups, mail not configured, last send failed, #340). It only reads: nothing on it changes the server or sends an email. It starts with mail and can take other checks later, each its own card.

  • Mail says whether a mail server is configured, which is whether SMTP_HOST is set. Without it the server has no fallback: every email fails with No mail server is set: SMTP_HOST is unset, nothing of it is printed to the log, and the card shows Not configured with the reason, in crimson with an icon. With it, the card says how the last email since the start went: sent, when and which kind (confirmation, password reset or test), or the mail server's error in crimson. The SMTP host, user and password are never shown.
  • Pending registrations lists the accounts whose email isn't confirmed yet, newest first (the last 100): the address, when it signed up and when its latest confirmation link expires. Signing up again sends a new link, so the date moves. No email is sent from here and there is no action on a row; on a laptop with no mail server, this is where a developer sees who signed up, and confirms them in Postgres (Trying it locally).

The routes are GET /api/v1/admin/status ({mail: {configured, lastSend: {at, kind, sent, error} | null}}) and GET /api/v1/admin/pending-registrations ({registrations: [{email, signedUpAt, linkExpiresAt}]}), for an admin signed in through the website.

The public side is the web app's /status page (mockups, down), which anyone can open. It asks GET /api/v1/status and shows only whether Coach Poulpy is up or down, down too when the server can't be reached; it never says how the server is configured, and a test holds it to that.

Catalog ​

The server holds the exercise catalog as a catalog draft the admin edits and numbered published versions that phones download, each exercise stored on its own as revisions, so a publish writes only the exercises that changed (catalog_exercise_revision, catalog_version; ADR 0026, #337). The screens are #338; the routes come first.

  • The first start seeds it from the catalog the server was built with: that version becomes the first published one and its exercises the draft. Later starts leave it alone.
  • An exercise in the draft is the catalog's JSON, every text a map from language to string ({"en": "Goblet squat", "fr": "Squat gobelet"}). Saving needs the English name; the other shipped languages can wait.
  • A slug is editable only until the exercise is first published; after that a rename is refused (409 slug-published), since workouts point at it (ADR 0008). Exercises are retired, never deleted, and a retired exercise can be offered again; an edit keeps an exercise retired or offered.
  • Publishing makes the draft the next version, numbered past both the latest published one and the bundled one, with the variation groups as they were. Only the exercises the draft changed get a new revision. It is refused while a name, instruction or variation note lacks English or French (409 missing-translations, listing the exercises and languages), or when nothing changed (409 no-changes). GET /api/v1/catalog serves the new version at once.
  • Every write goes to the audit log: admin.catalog.create, admin.catalog.edit (a rename reads old -> new), admin.catalog.retire and admin.catalog.offer with the slug as the target, admin.catalog.publish with the version number.

The routes, for an admin signed in through the website, are:

  • GET /api/v1/admin/catalog/exercises with q (part of the slug, a name in any language or an alias), retired (yes/no), sort (catalog, the default and the catalog's order, name, pattern, languages, change, status), order (asc, the default, or desc), page and size (20 by default, up to 100), answering one page as {exercises: [{exercise, published, change}], total} (a word that isn't allowed is a 400 bad-query). published says whether a version holds the exercise, so whether its slug is still editable; change is added, edited, retired, offered or null against the latest version. Sorting by languages puts the exercises missing a language first, and by change the changed ones first.
  • GET /api/v1/admin/catalog/exercises/{slug}, one exercise in the same shape.
  • POST /api/v1/admin/catalog/exercises with an exercise (201, 400 invalid-exercise with a reason, 409 slug-taken).
  • PUT /api/v1/admin/catalog/exercises/{slug} with the whole exercise; a different slug in the body renames it (404 unknown-exercise, 409 slug-published, 409 slug-taken).
  • POST /api/v1/admin/catalog/exercises/{slug}/retire and POST /api/v1/admin/catalog/exercises/{slug}/offer, which offers a retired exercise again.
  • GET /api/v1/admin/catalog/changes: what publishing would do, {version, nextVersion, added, edited, retired, offered, missing}, each change a {slug, name} and each missing entry {slug, name, languages}. An edited exercise also has fields: each changed field as {field, before, after}, with before from the latest version and after from the draft (null where absent). A text is one field per language and instruction (name.fr, instructions.1.en); a list of plain values (muscleGroups, equipment) is one field.
  • POST /api/v1/admin/catalog/publish: {version}, or the 409s above.

Making the first admin ​

No endpoint makes an admin. Set ADMIN_EMAIL in the production environment (Releasing) and deploy: when the server starts, the confirmed account with that address becomes an admin. An address with no confirmed account does nothing, so signing up first with someone else's address cannot take the role. The promotion is written to the audit log.

The audit log ​

An admin action is an AdminAction event (who, what, the target), sent through http4k's Events like any other event. One sink stores it in the admin_audit table (who is empty when the server itself did it, as at start-up; rows stay when the admin's own account is deleted), and another prints it to the server log, which the log shipping picks up. GET /api/v1/admin/audit returns the last 100 rows, and the first screen of the admin shows them. Each admin feature emits an AdminAction for its writes; tests check it with RecordingEvents.

Sensitive values are values4k types that print masked: EmailAddress prints as a***@example.com, so an address that reaches a log or an event by accident stays hidden, and the real one is read with .value only where it is needed. An event never carries a password or an unmasked address.

What comes next ​

The catalog's screens (#338), editing variation groups, and a tool that copies a published version back into the repository's catalog files so the next build bundles it (ADR 0026). The status will take more checks, such as the database and the catalog version, and log viewing is its own issue.
