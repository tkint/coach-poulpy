Architecture ​

Coach Poulpy is local-first: the mobile app holds the whole domain model and runs alone as a guest on family phones, and the server and website join later as a sync and sharing layer over the same model. One Kotlin Multiplatform core owns the domain, the workout engine and the database on Android and iOS, so the two apps cannot drift apart. The decisions behind this are recorded as ADRs; the words are defined in the glossary.

Delivery phases ​

Each phase adds a layer without reworking the one below it, because the domain, engine and storage are already shared. Phase 2 runs alongside phase 1 because the treadmill link was the riskiest piece. GitHub milestones follow these phases.

Domain model ​

Every workout shares the same concepts, whatever its format. Planned content is versioned and immutable per version, so a session always points at the exact version it followed, a synced library entry follows the latest version, and a copy forks from one.

ConceptWhat it holds
ExerciseStable slug, names in French and English, movement pattern, muscle groups, equipment needs (each a list of alternatives) and optional equipment, measurement (reps, time, distance, hold), per-side flag, images, instruction steps
WorkoutName, format (circuit or sets), parts (an optional warm-up, one or more work parts, an optional cool down) each holding a tree of steps, estimated duration, tags
StepAn exercise step (exercise, prescription, and a role: exercise or recover), a group (sequence, superset, circuit, interval set with rounds), or a rest
PrescriptionSets, and per set a target (reps, duration, distance, hold), an optional load, intensity (RPE, speed, incline, heart rate zone), tempo, and rest before the next set
PlanName, goal, weeks of days, each day holding zero or more workouts
EnrollmentA person following a plan version from a start date, with one calendar entry per scheduled workout (planned, done, skipped, moved)
GoalA measurable target with an optional deadline, computed from sessions
SessionOne workout actually done: start and end, source (guided, free, device only), optional link to the planned workout version and calendar entry, set results, samples, notes, effort and pain

Statistics are derived, never typed in. core/stats computes metrics from sessions: personal records, weekly load and goal progress all come from the same computation, on the phone for guests and on the server for accounts.

Sharing and coaching add three small concepts: a library entry (synced or copy), a coach link (status, revocation date) and a comment attached to a session, a set result or a calendar entry.

Formats, parts and the engine ​

A workout's format is chosen when it is created (ADR 0013):

FormatBuilt asAn exercise holds
CircuitRounds through several exercises: a repeat around themOne set: reps, time or hold and a load; a walk or run has a duration and an intensity
SetsOne exercise at a time, all its sets, then the next; repeats for supersetsIts sets, each with a target and load, and the rest between sets

Its parts run in order: an optional warm-up, one or more work parts, an optional cool down. How a step finishes comes from its target alone: a time or a hold runs a timer; reps, a distance (unless a treadmill reports it) or "until button press" wait for a tap.

The engine compiles a workout into a flat timeline of work, rest and transition phases, then runs it as a state machine that the UI only observes. The clock is injected, so the engine is testable without waiting. It emits cues (3-2-1, switch sides, next exercise) that each platform turns into sound, vibration and text. Every action is a session event written at once, so a killed app resumes at the same second.

Storage and sync ​

  • The phone database is the source of truth; the server is a replica (ADR 0001).
  • Ids are UUIDv7 made on the device (ADR 0005).
  • Sessions never conflict; workouts and plans keep both edits; small fields take the latest write (ADR 0006).
  • The website is online-first, using the same push and pull calls, and buffers a running session's events in IndexedDB.
  • The catalog ships with the app and updates without an account (ADR 0008).

Devices ​

A treadmill is the first metric source: anything that turns a device into timestamped samples (speed, incline, distance, heart rate, cadence). The engine only sees samples. On Android a session runs in a connected-device foreground service; on iOS the Bluetooth background mode with state restoration keeps recording on a locked phone. A dropped link is retried for 60 seconds while the session keeps its timer, and the gap is marked in the samples rather than filled. Many treadmills send only some FTMS fields, so the decoder reads the feature flags first and the UI hides what a machine does not send.

Accounts and security ​

  • A guest's data never leaves the phone; the operating system's file encryption protects it.
  • Sign-up pushes the whole local database as a first sync, keeping ids.
  • Email and password hashed with Argon2id, plus Sign in with Apple and Google, whose ID tokens the server verifies.
  • 15-minute access tokens and rotating refresh tokens stored hashed; Keychain or Android Keystore on phones; an HttpOnly, SameSite cookie on the web.
  • One http4k filter resolves the user, every query is scoped by owner, and coach access is checked against an active coach link on each request.
  • Health data is sensitive under the GDPR: consent at sign-up, export as JSON and FIT, full deletion, hosting in the EU.

Deployment ​

The first release needs no server. Android phones install the signed APK from CI; iPhones need Xcode (7-day installs with a free account) or TestFlight with a paid Apple Developer membership. The server builds into one JVM program that can run in a container, on a VPS or on a managed platform, chosen when accounts go live.
